# 聊天文字调色（SillyTavern 扩展）

给酒馆聊天消息改色的 UI 扩展：主要文本、斜体文本、引用文本三类文字可**分别**调色，支持「跟随主题 / 纯色 / 渐变」，渐变可自定义 2~4 个颜色与角度、带霓虹光晕开关与强度，并内置 10 套配色预设与 3 套可保存的自定义预设。面板跟随酒馆主题与字体大小。

## 安装

1. 把本文件夹整体复制到酒馆的用户扩展目录：

   ```
   SillyTavern/data/<你的用户名>/extensions/聊天文字调色/
   ```

   最终结构为：`extensions/聊天文字调色/manifest.json`、`index.js`。

2. 重启酒馆（或刷新页面）。
3. 进入 **扩展（Extensions）→ 管理扩展**，确认「聊天文字调色」已启用。
4. 打开 **扩展设置**，找到「聊天文字调色」面板开始配置。

## 功能对照

| 需求 | 实现 |
| --- | --- |
| 只改聊天消息 | 染色仅作用于 `#chat` 内的消息，不碰角色卡、设置等其他界面；代码块（行内 `code`、`pre`）保持原样 |
| 插件总开关 | 面板顶部「启用聊天文字调色」开关，一键停用/恢复；停用后聊天保持酒馆原生样式 |
| 三类文字横排切换 | 面板顶部横排「主要文本 / 斜体文本 / 引用文本」标签，逐类设置 |
| 跟随酒馆主题 | 每个类别都提供「跟随主题」模式，不做任何处理；面板配色、字体大小跟随酒馆 |
| 纯色 | 可选任意颜色（色块 + Hex 输入 + 取色器） |
| 渐变 | 自定义 2~4 个颜色（可添加/移除），角度 0~360° 可调 |
| 光晕 | 渐变模式下有「霓虹光晕」开关与强度（0~100%）；逐字三层 `text-shadow` 辉光，每个字散发自己颜色的光晕（蓝段蓝光、白段白光、黄段黄光） |
| 流式实时渐变 | 流式期间和结束后**同一套**逐字染色：每个字一出现就拿到自己的渐变颜色和同色光晕，真正「渐变 + 光晕」，不是整段一个色。关键是重建在 `MutationObserver` 回调里**同步完成**（MO 回调是微任务，早于浏览器下一次绘制），所以不会有「中间一帧退回单色兜底」的跳变；只有连续重建失败才会退回兜底。 |
| 单一发光来源 | 一条消息只要被逐字染色，元素本身的渐变/滤镜就全部让位（元素级规则带 `:not([data-yyx="1"])` 互斥），光晕只由每个 span 的 `text-shadow` 承担；未染色/正被重写的过渡态则由元素级 `text-shadow` 承担。**全流程不再使用 `filter: drop-shadow` 发光**（真机证明手机端元素级 filter 完全不出光） |
| 渐变粒度 | 主要文本 = 整条消息；**斜体 = 每对 `*xxx*`（一个 `em`）独立循环**；**引用 = 每个引号内对话独立循环**（引号外叙述保持酒馆原色，按字符顺序首→尾） |
| 内置预设 | 10 套配色预设位于配色设置下方；点击套用：斜体与引用应用渐变并开启光晕（强度 100%），主要文本改为跟随主题 |
| 自定义预设 | 3 套可保存槽位，调好配色点「存入」，点「使用」一键切换 |
| 取色器 | 参考常见拾色器：色板（饱和度/明度）+ 色相条；右侧依次为色值预览、Hex、RGB 与确定按钮，实时联动 |

## 使用说明

- **切换类别**：点击顶部标签（主要文本 / 斜体文本 / 引用文本），下方显示该类别的配置。
- **配色模式**：跟随主题 / 纯色 / 渐变，切换后显示对应选项。
- **渐变颜色**：每行「色块 + Hex 输入 + 调色板按钮」，点击调色板按钮展开取色器；最多 4 色、最少 2 色，可点「＋添加颜色」在末尾前插入中间色，「－」移除。
- **光晕**：勾选「霓虹光晕」后出现强度滑块；每个字单独散发「该字颜色」的三层 `text-shadow` 光晕（贴字亮边 + 中层 + 外晕），强度控制光晕半径与透明度，100% 即原始霓虹参数；低强度档仍保留可见辉光，强度拉到 0 或关闭光晕则完全无光。
- **内置预设**：点击色卡即套用（斜体与引用应用渐变并开启光晕 100%，主要文本改为跟随主题），套用后可再逐类微调。
- **自定义预设**：调好某一类别的渐变配色后点「存入」保存到槽位；点「使用」把配色套用到斜体与引用，主要文本改为跟随主题。
- **总开关**：面板顶部勾选「启用聊天文字调色」生效；取消勾选即停用（聊天保持原生样式），再次勾选恢复配色。
- **实时生效**：修改后即时重染可见与后续消息；流式生成期间也是逐字渐变 + 每字同色光晕（正文被重写时在同一帧内重建，不会出现"整段单色"的中间帧）。
- 「重新渲染可见消息」手动清理残留染色并重载配色样式；「全部恢复跟随主题」一键还原（自定义预设槽位保留）。

## 设计说明

- **光晕观感**：每个字单独上色并单独发光——文字先按渐变方向逐字取色，再给每个字加同色三层 `text-shadow`（贴字 `2px/1.0`、中层 `8px/0.85`、外晕 `24px/0.50`），蓝段蓝光、白段白光、黄段黄光；以最高优先级（!important）写入，避免被主题样式覆盖。
- **性能**：
  - 逐字染色按需触发（设置变化 / 生成结束 / 消息进入视口），流式期间同样逐字染色，重建在 MO 回调内同帧完成（不出现中间帧），只有连续失败才退回元素级渐变 + `text-shadow` 光晕兜底；
  - 主要文本按字符在渐变方向上的真实位置投影取色；斜体每对 `*xxx*`、引用每对引号各自按字符顺序线性取色（首→尾），跨行连续、方向不反转；引用引号外叙述不染色；
  - 光晕为逐字 `text-shadow`，不创建 filter 合成层，长文本性能更稳。

## 注意事项

- 若同时启用了带光晕/渐变的 UI 主题：主题对 `q`/`blockquote` 自带的光晕与渐变会与插件效果叠加，建议二选一，或在插件中关闭对应光晕。
- 斜体与引用嵌套时，以斜体的设置优先（斜体文字按斜体规则染色）。
- 若「主要文本」设为渐变、而斜体/引用为「跟随主题」：主要文本整条渐变会作用于整条消息，斜体/引用文字也会呈现主要文本的渐变；如需各司其职，请为斜体/引用分别选择纯色或渐变（推荐直接使用内置预设，主要文本会自动设为跟随主题）。
- 流式输出期间即逐字染色（与结束后同一套），新增字符只追加、不重建已有 span，不再有「先近似、后校正」的切换过程。
- 建议配合酒馆设置：开启 **No Blur**、关闭「流式淡入」动画，观感更稳定。

## 版本

v1.2.7（流式期间恢复逐字渐变 + 每字同色光晕，且不闪：重建搬进 MO 回调同帧完成）
- v1.2.6 用「流式锁定」消掉了闪烁（真机确认「确实不闪烁了」），但代价是流式期间整段只有一种呈现：元素级渐变 + **色标首色**光晕。粉蓝这种配色下每个字都在发粉光，把中段的白色、尾段的蓝色都糊成粉色，观感就是「一刀切」——这是用户不能接受的。
- 结论：兜底只能在整段用**一个**光晕颜色，而「渐变 + 光晕」本质要求**每个字发自己颜色的光**，所以流式期间必须走逐字 span，无法用元素级规则替代。
- 那为什么之前逐字染色会闪？因为重建发生在**延迟执行**（防抖 / 定时重染 / 事件重染）里：酒馆抹掉 span 之后，画面会先按元素级兜底渲染一帧或多帧，再跳回逐字版 —— 两帧观感不同就是肉眼看到的「闪」。
- 修法：把重建搬回 `MutationObserver` 回调里**同步**执行。MO 回调是微任务，跑在浏览器下一次绘制之前，因此「被抹掉 span 的那一帧」根本不会呈现 —— 屏幕要么是上一帧的逐字版，要么是新一帧的逐字版，中间没有单色兜底帧。
- 兜底仍保留（元素级渐变 + 首色 `text-shadow` 光晕），但只在**同一条消息连续 3 次同步重建都抛异常**时启用并锁定到本轮生成结束，属于故障兜底，不参与正常渲染。
- 其他：`GENERATION_ENDED` / `STOPPED` 时仍做一次精确重建（合并了原来的 3 次全量重染 + 连打），收尾不再重复整条重染。
- 诊断信息：`flicker.modeSwitches` 必须为 0（兜底 ↔ 逐字来回切次数）；`perf.byKind.full` 现在会显示流式期间的重建次数与单次耗时（若单次耗时很大，说明这台设备上整条重建偏慢，可据此再优化）；`lock.marked` 应保持 0（只有故障才会变成 >0）。

v1.2.6（流式锁定：一种呈现到底，彻底消除「兜底 ↔ 逐字」交替闪烁）
- v1.2.5 的真机回测（三层光晕，诊断 dump 19204B）：整轮生成 `mutations = 77`，`perf.byKind.full = { n: 18, last: 300, max: 486 }` —— 说明流式**中途仍然发生了十几次整条重建**，每次 300~486ms。每次重建都是一次「呈现形态切换」：兜底（整段首色光晕）→ 逐字（每字同色光晕）→ 下一个 chunk 又被打回兜底。用户描述正是「所有渐变字首色+光晕 与 渐变+光晕 交替闪」。
- 那些中途重建来自四条路径，都不是 MO 同步路径：① 静默超过 1.2 秒的尾随排程（`scheduleMes`）；② `MESSAGE_RECEIVED` / `MESSAGE_SENT` 触发的 `repaintAll`（流式分支对每条消息都整条重染）；③ 守护帧与 `fastPaintBurst` 在 900ms 静默窗口过后补染；④ 结束时的 3 次全量重染 + 一轮连打（一条长消息被重染 4~8 次）。
- 修法：**流式锁定（stream lock）**。正在生成的那条消息被打上 `data-yyx-stream` 标记后，上面四条路径**全部跳过它**（诊断里 `lock.skips` 记录挡掉的次数），直到 `GENERATION_ENDED` / `STOPPED` 才统一解锁。解锁后只做**一次**精确重建（不再 3 次全量 + 连打），后续只补「确实还缺染色」的消息（`mesNeedsPaint` 判据）。120 秒「ENDED 丢失」兜底改为每次收到新 chunk 都重置，避免超长回复被误判结束。
- 因此流式全程只有一种观感：元素级完整渐变 + 首色光晕，不闪；生成结束的那一瞬间做唯一一次升级，变成每字同色光晕。
- 诊断信息新增：
  - `flicker.fallbackFrames` / `flicker.modeSwitches` —— 前者是尾条消息处于兜底的帧数（流式期间应≈`frames`），后者是「兜底 ↔ 逐字」来回切换次数，**必须是 0**，>0 就说明还在闪。
  - `lock: { marked, skips, lockedNow }` —— 这一轮锁定了几条消息、各路径因此跳过了多少次重染、此刻还有几条锁定中。
  - `lastMes.mesShadow` / `lastMes.mesFill` —— 兜底态没有 span，光晕要看 `.mes_text` 自己生效的 `text-shadow`（`none` 才代表肉眼无光）。

v1.2.5（真机根因修复：流式中不再逐段整条重建，兜底改用 `text-shadow` 发光）
- v1.2.4 的真机诊断给出了决定性证据：`perf.byKind = { full: { n: 271, last: 197, max: 426 }, chars: { n: 15 } }`。也就是说流式期间插件做了 **271 次"整条消息重建"**（每次 197~426ms），而廉价的新字增量染色只跑了 15 次。酒馆每吐一个 chunk 就把整段正文重写一遍、把逐字 span 全抹掉，插件只好整条重染；这几百毫秒里画面只能靠元素级兜底，而该手机设备上元素级 `filter: drop-shadow` **根本不出光** → 长消息大约每 0.6 秒一亮一暗。同时 `glowMode` 已被切到「一层」仍照闪，证明**跟光晕层数无关**；也解释了"前十几秒不闪"——字少时重建只要几十毫秒。
- 修法一：**兜底也发光，且不用 filter**。元素级渐变分支不再输出 `filter: drop-shadow(...)`，改为 `text-shadow: <光晕>  !important` + `filter: none !important`，与逐字 span 用的是同一套发光机制（桌面 Edge 对照实验证明元素级 `background-clip: text` + `text-shadow` 能正常发光、字内仍是渐变）。
- 修法二：**流式期间不再逐段整条重建**。检测到正文被整段重写（span 被抹）时，不再同步 `paintNow` 重建，只打 `data-yyx-stream` 标记交给元素级兜底，并进延迟队列；重排延迟在流式期间抬到 **1.2 秒尾随防抖**（每次新 chunk 都重置计时），守护帧与可见修复在最近 900ms 内有变动时直接跳过。生成结束（或发送停止）时一次性精确重建，`repaintAll` + `fastPaintBurst` 多枪确保补齐。新字增量（`paintChars`，2~3ms）路径原样保留，span 没被抹掉时仍然立即上色。
- 修法三：**兜底光色取色标首色**，不再取中点色。像粉蓝（`#ffb6c1 / #ffffff / #a8d8ff`）这种"中间是白"的配色，用中点色发光会在暗底糊成白雾、把整段渐变冲淡——这正是历史反馈里"流式中偏灰白"的来源。
- 代价（如实说明）：流式过渡期（正文刚被重写、还没到静默阈值）呈现的是**元素级整段渐变 + 整段首色光晕**，不是"每字散发自己颜色的光"；安静下来或生成结束后会自动升级为逐字同色光晕。这是为了彻底消除"有光/无光交替"必须付出的取舍。
- 诊断信息：`perf.byKind.full` 的 `n` 现在应显著下降（流式期间几乎只剩末尾一次重建）；`lastMes.stream` / `baseSpans` 可确认当前处于"兜底过渡"还是"逐字完成"。

v1.2.4（光晕渲染档位 + 绘制耗时诊断）
- 1.2.3 的真机诊断显示：流式期间 `bareFrames = 0`、`lagChars = 0`、`guard.fixes = 0`、`baseTotal/baseSpans` 与当前完全一致——也就是**逐字 span 一直是齐的、每帧都有光晕**，`glowNow` 也确实是非 none 的三层阴影。闪烁不再是"补染没跟上"，而只能是**渲染/光栅化层面**：一条几千字、上千个发光字的消息，每个字 3 层高斯模糊阴影，手机上累积的光栅化工作量很大，越写越长越容易出现整块重绘闪动。这与"前十几秒不闪、后来才闪"的高度吻合（前十几秒字数少）。
- 新增面板「光晕渲染」档位（全局，即时生效，`restyleAll` 原地重刷不改结构）：
  - **三层（默认，最亮）** —— 与之前完全一致的观感
  - **两层** —— 少一次模糊，观感接近
  - **一层** —— 最省，长文最稳
  切到「一层」如果闪烁立刻消失，就证明是光晕光栅化成本导致的，我可以据此把默认档改成自适应（长文自动降档）或者换更省的发光的实现。
- 诊断信息新增 `perf`：`calls / lastMs / maxMs / avgMs / slowOver16ms / byKind`（每次补染的 JS 耗时，`maxMs` 很大说明是 JS 慢，很小但画面仍闪说明是光栅化慢）。
- 诊断信息新增 `cost`：`totalSpans / glowSpans / blurSumPx / glowMode / lastMesHeight`（全场发光字数量与模糊半径总量，直接量化"光晕成本"）。

v1.2.3（同步守护 + 启动即发光晕 + 观察器修复）
- 从真机诊断（1.2.2）看出：整段流式采样 `bareFrames = 0` 但 `syncPaints = 0`——说明流式期间插件一次都没补染过，不是"拍到无 span 的帧"，而是**补染停摆**。同时 `emSpans/qSpans` 出现 0，消息已经是"染了一部分就停住"的半成品。
- 新增**同步守护**（每帧自检）：流式期间用 `requestAnimationFrame` 每帧用极便宜的判据检查最新 3 条消息——文本比上次染完时长、或 span 变少，就立刻同步补染。它不依赖 MutationObserver 是否健全，所以观察器丢失、事件漏发、容器被重建都能自愈。`guard.fixes > 0` 就是"守护替观察器补了多少次"。
- **观察器补订 `characterData`**：酒馆流式有两种写法（整段重写 / 只改文本节点），原来只订 `childList`，后者一个通知都收不到。
- **容器重建自动重挂观察器**：重启/切聊天后酒馆会重建 `#chat`，旧观察器绑在废弃节点上，后续 chunk 全部失效。现在每帧检查容器是否换了，换了就重挂。
- **启动即发光晕**：原来启动只排了一次 50ms 防抖，撞上"消息还没布局（宽高为 0 被跳过）"就会退化成"先看到渐变、过几秒才冒光晕"。现在改为立即同步修复 + rAF + 120/350/800/1600ms 连打数枪，只补"确实缺染色"的消息，开销可忽略。

v1.2.1（修流式闪烁：同一帧内同步补染）
- 真机截图确认了闪烁的确切成因：**无光的那一帧是元素级路径，有光的那一帧是逐字路径**。也就是说在该设备上只有逐字 span 的 `text-shadow` 真能发光，元素级 `filter: drop-shadow` 不出光。而酒馆每吐一个 chunk 都会整段重写消息正文，把 span 抹掉；旧版是延迟 60ms 防抖才补染，中间那几帧就落到了「元素级、不发光」的路上 → 有光/无光交替。

- 结构还在（只是文字变多）时走增量补染，已有 span 原地复用、不重建；结构被整段抹掉时才整体重染。
- 加了文本指纹（`MES_SIG`）：自己写入 DOM 会产生回声回调，指纹一致且仍有 span 时直接忽略，既防「重染→再触发→重染」死循环，也省掉无谓的重排。
- 长消息（>2200 字）不逐 chunk 同步重排，退回 60ms 防抖，避免手机端卡顿。
- 同步重染全程 try/catch，异常不会中断后续 chunk，最坏情况退回防抖 + 元素级兜底。

v1.2.0（重构：彻底改为「一条消息只有一个发光来源」）
- **症状根因**：旧版同一条消息上并存两套上色与两套发光——元素级 `background-clip:text` 渐变 + `filter: drop-shadow`，以及逐字 span 实色 + `text-shadow`。哪一套生效取决于「这条消息此刻有没有逐字 span」，而流式每个 chunk 都会让 span 有无反复变化，于是出现你反馈的三个现象：开局只有元素级近似（短文本只取到首色段，看着发淡）、流式期间光晕在两套机制间来回切换（一闪一闪）、调强度时先拆 span 再重建（中间那一帧两套都不生效，光晕消失）。
- **重构口径**：以逐字 span 作为唯一载体，颜色与光晕都写在每个字自己的 span 上；元素级渐变与 `filter` 只保留给「尚未逐字染色」的消息做过渡，并加 `:not([data-yyx="1"])` 与逐字染色严格互斥，两者永远不会同时作用于同一条消息。
- 已染色的消息追加一条中性规则（`background:none`、`background-clip:border-box`、`-webkit-text-fill-color:currentColor`、`text-shadow:none`、`filter:none`），保证祖先元素不会用文字裁剪层把子 span 的光晕一起裁掉。
- 流式改为增量染色：`paintStreamChunk` 不再只贴元素级兜底标记，而是直接逐字上色——已有 span 原地复用（组号 `data-yyxG` 与引号状态按元素续接），只给新出现的文字补 span，再对整条消息重算一次样式（带样式缓存，只写真正变色的字）。
- 设置改动分两类处理：模式/色标/角度变了才重建 span（`structSig` 结构签名判定）；只改强度、光晕开关或纯色时**原地重刷**每个 span 的 `text-shadow`，绝不拆 span，因此拖强度不会再出现光晕掉一帧的现象。
- 调试采样改为取**最新的两条消息**并附全局计数（总消息数、已染色条数、span 总数、屏幕附近未染色数）。旧版一直抽样最早的消息，而那些消息通常在视口外、按设计就不染色，导致诊断里长期显示 `spanCount: 0`，掩盖了真实状态。
- 升版为 1.2.0（行为与实现均重构）。
